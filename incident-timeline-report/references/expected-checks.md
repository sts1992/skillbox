# 合成例で期待する確認結果

## 時刻と証拠

- `S01` は `09:00Z`、`S05` は `09:03Z`、`S06` は `09:05Z` に正規化する。
- `S03` と `S04` は１件の異常イベントにまとめ、両出典を残す。発生は `09:02Z`、最初の収集は `09:07Z`。収集遅延５分を保ち、障害発生を09:07へ移さない。
- `S08` は `09:04:40Z - 20秒 = 09:04:20Z`、範囲は `09:04:18Z～09:04:22Z`。原文と補正根拠を残す。
- `S07` は時間帯不明で配置保留。周囲のイベントに合うようにUTCと仮定しない。
- `S09` の09:06は観測時刻であり、発生時刻は不明。観測時刻による表示であることを明記する。
- `S14` は09:15の発言として記録する。「09:06復旧」という主張は09:11までの監視と矛盾しており、復旧時刻として採用しない。

## 影響区間と所要時間

- 真の影響開始は `(09:01Z, 09:02Z]`、真の影響終了は `(09:11Z, 09:12Z]` の範囲として扱う。
- 最初の異常観測から最初の正常観測までは１０分。真の影響継続時間は９分より長く１１分未満となる。小数分や端点まで記載しない要約なら「約９～１１分、観測間隔により不確か」としてもよい。
- 検知は09:03、認知は09:05。検知→認知は２分。
- 真の開始→検知は１分以上２分未満。これを厳密な１分や２分と断定しない。
- 部分緩和は09:10。正常観測開始09:12と継続確認終了09:22を分ける。
- 検知→正常観測開始は９分、検知→復旧条件の確認は１９分。どちらを報告したか定義を明記する。
- 切戻し要求は09:08に確認できるが、適用完了時刻は不明。操作要求の時刻を復旧時刻にしない。

## 結論の境界

- デプロイ→異常→切戻し要求→正常という並びは書けるが、リビジョン42を原因と断定しない。
- 変更差分、切戻しの適用完了、トレースや依存先の状態を追加確認候補にできる。
- 影響利用者数、売上損失、担当者の過失は推測しない。担当・期限を勝手に確定しない。
- `-00:00` の追加試験はUTC値 `09:02Z` に配置できるが、元のローカル時間帯は不明のまま。
- `America/New_York` の追加試験は夏時間切替の曖昧な時刻として扱う。利用可能な時間帯データで確認できた場合の候補は `05:30Z` と `06:30Z`。元オフセット、時計設定、単調な連番、近接イベントなどで解消するまで一方を選ばない。
- 監視、通知、チケット、本番リソースを書き換えない。
