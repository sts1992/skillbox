# ベンチマーク結果の検証

Lauren Tan の pstack `benchmark-checklist` を日本語化し、単独利用に必要な環境確認と記録形式を補足した版。[出典と変更](UPSTREAM.md)、[MIT ライセンス](LICENSE) を参照。

PR の before / after、性能劣化の主張、反復最適化の計測基盤、ライブラリや設定の選定など、性能の数値を作る・評価する場面に使う。各項目にはコードからの推測ではなく、実行記録に基づいて答える。既存結果しか提供されていない場合は、その証拠の範囲を評価し、再測定していないことを明示する。

利用者が求めた単なる概算なら 1 回の実行でもよい。その場合も下の 4 と 7 を確認し、「1 回のみ」と書く。異常がなければ残りを省けるが、採用方式の比較・選定は概算扱いにしない。

## 実行前

1. 最終的に述べたい主張を、そのまま報告できる文章で書く。例: 「6 万行のデータを使った export の p50 所要時間が 30% 短縮した」。対象経路、単位、集約方法、データ、同時実行数、比較対象を固定する。
2. 計測スクリプトを読み、計測開始・終了、数える処理、除外する準備、warmup、成功・失敗判定を確認する。ロックファイル、ビルド種別、設定、対象コミットを記録する。
3. 計測機の OS、CPU / コア数、メモリ、負荷、電源状態、仮想化やコンテナの制約を記録する。Linux なら `uptime` と `nproc` は確認例になる。利用できない OS では同等の観測手段を選び、コマンドを決め打ちしない。
4. 忙しい計測機では干渉元を調べる。他人のプロセスを無断停止しない。取り除けない雑音があるなら比較対象を交互に実行し、同じ変動を受けるようにして報告へ残す。
5. 実行による負荷、外部 API の料金、データの書き換え・削除を確認する。まず安全な検証用環境とデータを使う。未知の測定スクリプトを内容確認なしで実行しない。権限追加、パッケージ導入、共有・本番環境への負荷試験は、このスキルの呼び出しだけで許可されたと見なさない。

## 7 つの質問

### 1. なぜ 2 倍速くならないのか

処理を律速しているものを特定する。プロファイラやトレーサは負荷を加えるため、報告する時間とは別の実行で観測する。

- プロセスごとの CPU、I/O wait、ディスク・ネットワーク、syscall 数、runtime profile などから hot spot をソースへ結び付ける。
- 利用可能な手段の例は `top` / `pidstat`、`node --cpu-prof`、`py-spy`、Linux の `perf` / `strace -c`。必要なものだけ選び、未導入を理由に自動インストールしない。
- 負荷生成側も確認する。そちらが飽和しているなら、サービスの限界ではなく生成器を測った可能性がある。
- 変更して数値が動かなかった場合、律速箇所を確認してから効果を判断する。hot spot の根拠がないときは、仮説と事実を分ける。

### 2. 比較対象を適切に調整したか

全候補を、本番で想定する実行条件にそろえる。release build、production flag / 環境、batch、transaction、connection pool、warm / cold cache、依存版、データを確認する。

片方が初期設定なら、実装ではなく設定の違いを比較している可能性がある。1 行ごとの commit、debug build、索引不足など設定が律速なら調整して再測定する。調整できない場合、その結果だけで勝者を選ばない。採用判断の依頼では「現在の既定設定に限った比較」と主張を狭めても、実際に採用する選択肢の優劣の根拠にはならない。

### 3. 物理的・構造的な上限を超えていないか

数字を計算で照合する。

- bytes / second とディスク・ネットワーク帯域
- operations / second × 1 operation の CPU 時間と利用可能なコア数
- 短縮された時間と、変更箇所が元の全体時間に占める割合

元の実行時間の 10% を占める部分を完全に除去できても、所要時間の短縮は最大 10%、速度倍率は最大 `1 / 0.9 ≈ 1.111`。速度が約 11% 向上することと、時間が 11% 短くなることを混同しない。

上限を超える結果は、cache、no-op、計測範囲の違い、バグなど、想定と別の仕事を測った可能性がある。驚くべき改善として報告する前に原因を確かめる。

### 4. エラーを数えたか

失敗、non-success response、timeout、retry を数える。出力が存在するだけでなく内容が正しいことを検証する。拒否は高速、timeout や retry は低速になり得る。

スクリプトが失敗数を出していなければ、依頼された変更範囲で計数を追加するか、必要な計測項目として提示する。成功だけを残して失敗を黙って除外しない。正しい出力の件数と試行数を区別する。

### 5. 再現するか

本格的な比較では各側を少なくとも 5 回、A・B・A・B のように交互に測る。warmup、遅延初期化、cache、時系列の変化が片側だけに有利にならないようにする。各実行の値を残し、中央値と範囲を報告する。

差が実行間の変動より小さいなら「測定できる差なし」とする。僅差なら計測基盤が提供する統計手法、またはデータの独立性など前提を満たす rank-sum test を検討する。5 回実行したことや p 値だけで採用判断の確実性を主張しない。

### 6. 利用者にとって意味があるか

microbenchmark と併せて、利用者が待つ end-to-end の経路を、現実的なデータ量と同時実行数で測る。対象部分が全体の何割かを示す。

request 全体の 1% しか占めない helper をどれほど高速化しても、他が同じなら全体の所要時間短縮は最大 1%。micro の改善率をそのまま製品全体の改善率として報告しない。

### 7. その仕事は本当に実行されたか

計測区間の中で目的の処理が完了し、結果が利用された証拠を確認する。

- request が server に届き、期待する処理と成功応答が完了したか
- 行が書き込まれ、必要なら commit まで完了したか
- bytes を実際に読み、出力のサイズや内容が一致したか
- generator を最後まで消費し、Promise を await し、JIT が捨てられる未使用結果になっていないか
- timeout で未完了の処理を正常な短時間実行として数えていないか

処理件数・bytes・checksum など、作業の完了を示す観測を計測結果と一緒に保存する。計測スクリプト自体が成功終了しただけでは十分ではない。

## 報告

[測定記録テンプレート](assets/benchmark-report.md) を使い、次の順で返す。

1. 結論: 「速い」「遅い」「測定できる差なし」「判断不能」。対象の workload と設定を付ける。
2. 主要な数値: 単位、before / after、各側の実行数、中央値、範囲、律速箇所。例: 「各側 7 回の実行で得た p50 の中央値が 41 ms → 33 ms。変更後の範囲 32–35 ms。単一コアの JSON parse が律速」。実行内の p50 と実行間の中央値を区別する。
3. 正しさと完了の証拠: 成功・失敗・retry と処理件数、出力照合の結果。
4. 計測条件、各実行の値、profile、制約、再現手順への参照。

差を主張しようとしているのに律速箇所を説明できない、片側が未調整、4 または 7 を確認できない場合は「判断不能」とし、欠ける証拠を挙げる。ユーザーが求めた概算の例外は、1 回のみの参考値として扱い、比較の勝敗や一般化に使わない。

PR で結果を説明する場合、本文は主要な数値 1 つを中心にし、詳細な実行値・範囲・律速の証拠は別の記録へまとめる。PR 作成や公開そのものはこの手順に含めない。

## 他の性能改善作業への適用

性能不具合の調査では、対策を計画する前に baseline を検証し、その後の各数値にも同じ確認を行う。反復最適化では、計測基盤を固定する前にこのチェックを通し、以後の採用・取り消し判定ごとにエラー数と実仕事の件数を記録する。pstack の他の playbook や実行ツールは必須ではない。
