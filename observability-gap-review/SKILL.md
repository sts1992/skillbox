# 可観測性の欠落レビュー

## 入力と成果物

必須入力は、対象サービス、重要な利用者操作、調べたい障害または運用上の疑問、利用可能な計測資料とする。ダッシュボードだけでも着手できるが、収集系がないことと、資料がないことを区別する。

任意入力は、経路図、サービス所有者、SLI/SLO 定義、メトリクス一覧と型、label の種類・値の数、recording/alert rules、ログの安全な抜粋、trace の sampling 設定、collector の健全性、保管期間、障害の振り返りとする。

[レポート用テンプレート](assets/gap-review-template.md) を使い、体験と証拠の対応表、計測上の誤り、優先度付き改善案、費用とプライバシーの注意点、受け入れ試験を出力する。「ツールを追加すれば解決」と結論付ける前に、既存計測の意味と品質を調べる。

## ツール・安全・鮮度

- 最小構成はファイル閲覧と四則演算。接続先がなければ、提供資料の静的レビューとして完了できる。
- 接続済みの読み取り API があれば、サービス・環境・時間窓を限定し、少数の代表 query で確認する。全 retention 期間の無制限 query や高カーディナリティ列挙をしない。
- 利用可能なら、既存の `promtool` などでローカルに rule の構文を確認する。構文検証と本番データでの妥当性検証を区別する。ツールの導入は前提にしない。
- Web では [公式資料](references/sources.md) の対象バージョンを確認する。現行資料で推奨される機能が、対象 SDK・collector・backend でも使えると仮定しない。
- ダッシュボード、alert、sampling、retention、collector、instrumentation を変更しない。通知を無効化したり、負荷を発生させたり、計測データを外部サービスへアップロードしたりしない。
- 個人 ID、メール、token、cookie、本文、認証付き URL を取り込まない。既存のログや span に含まれる場合も報告へ転載しない。query に必要のない識別子を入れない。

入力ごとに採取時刻・集計窓・環境・schema/バージョン・サンプル数を記録する。古い query 定義と新しいメトリクスを無自覚に組み合わせない。直近 5 分の健康状態と 30 日の SLO 判定を混同しない。

## 手順

### 1. 利用者の体験を観測可能な問いへ分解する

重要な操作を 1〜3 個選び、開始点、成功条件、期限、失敗分類、非同期処理の完了点を書き出す。「CPU が高い」ではなく「注文が確定できないことを何で検出するか」を先に決める。

各操作について、入口、アプリ、依存先、非同期 queue、利用者側の順に証拠の所在を整理する。すべての層に同じ三種類の信号を要求せず、検出・切り分け・復旧確認に必要な観測へ絞る。

| 問い | 検出する信号 | 切り分ける信号 | 抜ける利用者・経路 | 信号自体の故障検出 |
|---|---|---|---|---|
| 重要操作が成功しているか | 対象を揃えた成功率 | 依存先エラー、関連 trace | edge で落ちた要求など | scrape/export の欠測 |
| 遅延・滞留が増えているか | 分布、queue の経過時間 | 飽和、依存先、処理段階 | timeout 前に計測されない要求 | collector の遅延・drop |

### 2. SLI の仕様と実装を分ける

1. SLI を実測の指標、SLO を対象期間における目標として記す。契約上の SLA を同じものと扱わない。
2. 比率型 SLI には eligible events、good events、測定地点、期間、集計単位を明記する。成功 code、利用者 cancel、bot、retry、timeout、部分成功をどう数えるか未定なら確認事項にする。
3. good と total は同じ母集団・同じ時間窓・同じ label 範囲から求める。retry を試行として数えるか利用者操作として数えるかを揃える。
4. ゼロ件を 100% に補完しない。無トラフィック、欠測、遅延取り込み、監視停止を区別する。分母ゼロや系列欠落の表示・alert 方針を記す。
5. 「300ms 以下の割合」と「p95 が 300ms 以下」を区別する。成功率と速度の周辺集計だけで「成功かつ高速」の件数を計算しない。
6. error budget を `1 - SLO`、比率型の burn rate を `観測された bad 比率 / (1 - SLO)` として扱う。適用条件は母集団・期間の定義が一致し、SLO が 100% でないこと。短時間の burn rate だけで期間全体の予算消費を断定しない。

測定地点が backend だけなら、そこへ到達しない失敗をどう測るかを欠落として扱う。利用者が未承認の SLO 目標を、レビュー担当者の推奨だけで正式値にしない。

### 3. メトリクスと query の意味を審査する

- counter、gauge、classic/native histogram、summary を識別する。名前の末尾だけで型を断定せず、定義を読む。
- counter は系列ごとに `rate`/`increase` を計算してから必要な軸へ集計する。window、scrape 間隔、欠測、reset、低トラフィック時の不安定さを確認する。
- インスタンス単位の成功率を平均せず、good の総数 / total の総数を求める。小さい母数を見えなくしない。
- summary の既計算 quantile や Pod ごとの p95 を平均して全体 p95 と呼ばない。classic histogram は必要な `le` を保って集計する。
- classic histogram で SLI 閾値の bucket がなければ、厳密値を出せるか確認する。補間値と厳密な件数を区別する。native histogram の採用は送受信側の互換性と費用を確認した提案にする。
- range、unit、label join、フィルタ、recording rule の依存、重複 scrape を確認する。実在しない metric 名を「動く query」として渡さない。

例として、以下は「全系列が同じ eligible requests を数える」ことを確認した後の候補であり、未確認環境へそのまま適用しない。

```promql
sum(rate(checkout_requests_total{environment="prod",outcome="success"}[5m]))
/
sum(rate(checkout_requests_total{environment="prod"}[5m]))
```

### 4. カーディナリティと保管費用を分けて評価する

1. 各 metric の label 名を、有限の業務分類、ターゲット識別、無制限の値、機密性のある値に分ける。request_id、user_id、raw URL、エラー本文を metric label に持つ設計を優先して見直す。
2. 理論上の組合せ上限を label の種類数の積で見積もる。ただし相関、存在しない組合せ、動的 churn を説明し、積を実測の active series と呼ばない。
3. classic histogram では有限 bucket 数に `+Inf`、sum、count を加えた系列増加を計算する。任意の追加系列があれば別計上する。native histogram に同じ計算式を適用しない。
4. active series、一定期間の新規 series、総サンプル量、保管期間、query 負荷を別に記す。label を一つ消す場合の分析機能の喪失も評価する。
5. 有限な route template、status class、必要な業務分類へ置き換える案を出す。詳細な相関は制限付きログ・trace・exemplar 等へ移す案を、機密性と互換性を含めて検討する。

予算は対象の規模と基盤の制約から決める。普遍的な「この系列数以下なら安全」を設けない。件数と単価が未確認なら費用削減額を捏造しない。

### 5. サンプリングと信号の欠落を評価する

- head sampling の決定時点と、tail sampling が観測できる範囲を記録する。上流で落とした trace を下流の tail sampler が復元できると考えない。
- エラーや遅い要求を優先する方針は診断には有用でも、保持された trace の比率を全要求のエラー率と同一視しない。正確な補正に必要な選択確率、母集団、欠落モデルがない場合は SLI 算出へ使わない。
- sampling と、queue overflow、export 失敗、フィルタ、retention 切れによる drop を分ける。設定値の sampling rate と、実際に backend へ届いた割合は同じとは限らない。
- trace の親子関係、service 間の context propagation、非同期リンク、late span、tail sampler の待ち時間・状態保持・負荷分散を確認する。実装固有の保証は固定バージョンの資料で検証する。
- SLI に使う件数と診断用に選んだ trace を区別する。代表性が未確認なら、別系統の全数 counter などによる照合を提案する。

### 6. 検出から行動へのつながりを確認する

alert ごとに、利用者影響、発火窓、継続時間、抑制・集約、通知先、所有者、runbook、復旧判定を確認する。alert が存在することだけを「検出できる」と評価しない。過去障害の再生やオフラインの rule テストを提案し、通知先への実際の発報は行わない。

改善案を「何が見えないか → 誤った判断の危険 → 最小の変更 → 検証方法 → 所有者 → 費用・機密性」の順に書く。優先順位は利用者影響、現在の盲点、実装負担で決め、製品や信号の数で評価しない。

## 検証と終了条件

- 算出値を再計算し、% と比率、秒と ms、サンプル数と系列数を取り違えていないか確認する。
- 既知の障害、正常な低トラフィック、ゼロ件、counter reset、欠測、sampling の変化を受け入れ試験に入れる。
- 提案 query は構文確認済み、資料上のみ確認、未実行を区別する。読み取り先を使えなければ架空の実測結果を作らない。
- 欠落の根拠と検証可能な次の一歩が揃い、変更を実行していないことを確認したら終了する。
- [合成入力](references/synthetic-observability.json) を読み、報告を書いた後に [期待事項](references/fixture-checks.md) で点検する。
