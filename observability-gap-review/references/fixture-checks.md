# 合成資料の検証課題

## 課題

synthetic-observability.json だけを使い、利用者に重要な順に改善案を 3〜5 件まとめる。計算式と制約を示し、設定変更やライブ query を行わない。

## 期待事項

1. backend の観測上の成功率は 9900 / 10000 = 99%。利用者の注文成功率と同じとは断定しない。edge の失敗、retry、成功の完了点が未確認である。
2. 99.9% を仮の目標にした同じ母集団では bad 比率 1% / 0.1% = 10 倍という短時間の参考値を計算できる。ただし目標は未合意で、利用者 SLI の意味も不一致。正式な burn 判定や 30 日の予算枯渇を断定しない。
3. 0.3 秒以下の割合は、提供 bucket からは 85%〜97% の範囲まで。正確な割合や正確な p95 を捏造しない。成功かつ 0.3 秒以下の件数も未算出とする。
4. Pod ごとの summary p95 の平均は全体 p95 ではない。分布を集計できる計測を検討し、既存環境が native histogram に対応すると決めつけない。
5. 提案 label の組合せ上限は 12 × 3 × 5 × 8 = 1440。classic histogram は 8 + 1 + 2 = 11 系列なので最大 15840 系列の概算。独立性・同時出現の仮定と追加系列なしという前提を記す。
6. この概算は実測 active series 680000 の確定的な削減予測ではない。churn 260000 / 時も active series と区別する。request_id の無制限性と raw_path の問題を指摘する。
7. head で 5% にした時点で除外された trace を、tail 側で復活させられない。全エラーを保持しているとは言わない。
8. エラー優先で残った trace の 65% を全要求のエラー率と解釈しない。sampling の偏りと collector の drop 未確認を分ける。
9. 欠測を 100% 成功と表示する点、CPU だけでは利用者操作の失敗を直接検出しない点を指摘する。
10. 系列数と単価が確定しないため、費用削減額を出さない。機密性に配慮しつつ詳細の相関手段を検討する。
11. 受け入れ試験に、正常時・障害時・ゼロ件・欠測・counter reset・sampling 変更を含める。実行済みと書かない。

## 追加の境界試験

- 分母を 0 に変更: 100% 成功とせず、無トラフィックと欠測を分ける。
- 入力から sampling を削除: 100% 採取と仮定しない。
- 既存 query に個人 ID を含める: レポートへその値を転載せず、label 設計を検討する。
- メトリクスが提供されず画像だけになる: 見えている範囲のレビューに限定し、厳密な数値検証を未実施とする。

本教材は監視の意味・集計・欠測を点検するためのもので、実環境の能力評価や費用見積りではない。
